# Review-loop redesign — Design Spec

**Дата:** 2026-07-06
**Задача:** `claude-tools-elf.23` (уточнение делверабла — скилл `review-loop` уже существует, PR #100)
**Статус:** согласован в брейншторме, готов к плану

## Goal

Ужесточить разделение ответственности между `/review-loop` и `flow:review-comments`:

- **review-loop** — ждёт конец пайплайна и оркеструет цикл (запуск/остановка).
- **review-comments** — ищет и обрабатывает замечания; сигналит, если замечаний нет.

Сигнал сходимости переезжает с «review-loop сам считает actionable-треды» на **«был ли новый пуш за итерацию»**. Плюс — поднять таймауты `review-gate` / `wait_for_checks`, чтобы не завершать ожидание за пару минут до медленного ревью Codex.

## Контекст (что есть сейчас)

`review-loop` (`.claude/skills/review-loop/`) каждую итерацию: ждёт пайплайн (`wait_for_checks.py`), **сам считает** actionable-треды через GraphQL `reviewThreads` (шаг 1d), и ветвит сходимость по этому счёту (шаг 1e). Это дублирует «что actionable» с `review-comments` и вынудило нас затащить в `review-loop` `isResolved`-логику (Codex round 2, коммент 3523239077). PR #100 прошёл 4 раунда ботов на текущем дизайне.

`review-comments` (`plugins/flow/skills/review-comments/`) — отдельный скилл, вызывается из `review-loop` через инструмент **Skill** (исполняется в том же контексте агента, не субагент).

## §1 Разделение ответственности

| | **review-loop** | **review-comments** |
|---|:---:|:---:|
| Ждёт конец пайплайна (`wait_for_checks.py`) | ✓ | |
| Красный пайплайн → сигнал + гейт «запускать RC?» | ✓ | |
| Запускает review-comments | ✓ | |
| Решает loop / stop / спросить (по `HEAD`-diff + сигналу) | ✓ | |
| Запрашивает и обрабатывает комменты | | ✓ |
| Владеет «actionable» (already_replied, resolved) | | ✓ |
| Сигналит «замечаний нет» | | ✓ |

`review-loop` **больше не считает треды сам** — это целиком в `review-comments`.

## §2 Итерация (control-flow)

```
a. HEAD_before = gh pr view <PR> --json headRefOid -q .headRefOid
b. PR не OPEN (merged/closed) → стоп
c. wait_for_checks.py <PR> <HEAD_before>
     exit 0  → зафиксировать список `failed` (чеки с conclusion не в {success,neutral,skipped})
     exit 1  → usage-баг вызова; чинить вызов, не трактовать как timeout
     exit 2  → timeout: plain-text prompt (НЕ AskUserQuestion):
                 1. подождать ещё   2. обработать сейчас (round = PARTIAL)   3. стоп
     exit 3  → head moved: ветка уехала во время ожидания → назад к (a)
d. ГЕЙТ красного пайплайна: `failed` не пуст → показать красные чеки, plain-text:
     1. всё равно запустить review-comments   2. стоп (чиню руками, потом перезапущу)
e. Запустить review-comments через Skill. Заметить его сигнал «замечаний нет» (§4).
f. HEAD_after = gh pr view <PR> --json headRefOid -q .headRefOid
g. РЕШЕНИЕ о сходимости → §3
```

Ожидание пайплайна (c) остаётся **до** запуска RC, потому что CI постит ruff/ty inline-комменты; считать/обрабатывать до окончания lint-джоба = пропустить их (early convergence). Это неизменно относительно текущего дизайна.

## §3 Решение о сходимости (заменяет старые шаги 1d/1e)

| `HEAD_after` vs `HEAD_before` | сигнал RC | round PARTIAL? | → действие |
|:---:|:---:|:---:|:---|
| изменился | — | — | **loop** → назад к (a) |
| не изменился | «замечаний нет» | нет | **чистая сходимость → STOP** |
| не изменился | «замечаний нет» | да (был timeout+process) | **partial hand-off → STOP** |
| не изменился | обработал (reply-only) | — | **спросить** plain-text: стоп / продолжить |

Пояснения:

- **«продолжить»** после reply-only → одна подтверждающая итерация: треды теперь `already_replied` → следующий RC вернёт «замечаний нет» → чистый стоп. Это осознанный выбор человека (не авто-петля).
- **partial hand-off**: если раунд PARTIAL (юзер выбрал «обработать сейчас» на timeout), даже «нет пуша + нет замечаний» — НЕ чистая сходимость. Репорт: «обработал что было, но пайплайн для `<HEAD>` не добежал (wait timed out) — перезапусти `/review-loop`, когда проверки завершатся». Сохраняется из текущего дизайна (фикс C9).
- Если дошли до STOP, но `failed` был не пуст (путь «всё равно RC» из гейта d) → финал НЕ «чисто», а «остановился, чек `<X>` красный — чини руками». `failed` красит финал.
- **Сходимость ≠ mergeable.** «Боты молчат» ≠ «готово к мержу». Резолв тредов и merge остаются за человеком (луп reply-only; `master`-ruleset требует резолва конверсаций живым человеком).

**Терминаторы:** сходимость (g) · PR merged/closed (b) · partial hand-off · юзер Esc · юзер «стоп» на гейте (d) или на reply-only-вопросе (g) · юзер «no» на Phase 3 внутри review-comments.

## §4 Сигнал review-comments «замечаний нет» (flow-scope, минимальный)

`review-comments` в своих терминальных состояниях «нечего обрабатывать» печатает **каноническую финальную строку-сентинел**, которую `review-loop` ловит:

```
FLOW-REVIEW-COMMENTS: no-actionable
```

Печатается в Edge Cases, где RC завершается без обработки: «No Unresolved Comments», «All Comments Already Replied», и когда после фильтра `already_replied` не осталось actionable. **Отсутствие** строки = RC что-то обработал (или запушил, или reply-only).

`review-loop` шаг (e/g): grep сентинела в исходе RC. Это единственная правка `review-comments` в рамках этой задачи. Resolved-фильтр GitHub-ветки — **отдельная** `claude-tools-elf.24` (отложена).

Почему сентинел, а не разбор прозы: детерминированный распознаваемый маркер устойчивее, чем интерпретация summary-отчёта, даже в одном контексте (агент может быть на много шагов дальше от запуска RC к моменту решения).

## §5 Что удаляем / что остаётся

**Удаляем из review-loop:**
- GraphQL-счёт actionable-тредов (шаг 1d) и всё ветвление сходимости на его основе (старый 1e). Уходит ~50 строк SKILL + вся `reviewThreads`/`jq`-простыня.
- Использование `gh api graphql` и `jq`. Из `allowed-tools` убрать `Bash(jq:*)` (больше не нужен); `Bash(gh:*)` остаётся для `gh pr view` в шагах (a)/(f)/(b).

**Остаётся (хардининг 4 раундов живёт):**
- `wait_for_checks.py` целиком — включая exit 2 (timeout → PARTIAL) и exit 3 (head-moved → restart). Его `failed`-вывод теперь кормит гейт (d) и красит финал (§3).
- Round-индикатор + `повторно`-трекинг, интерактивность вместо hard-cap, reply-only-caveat про skip-push.

**Переезжает, не выбрасывается:** `isResolved`-логика из счёта → в `review-comments` (elf.24).

## §6 Почему отложить elf.24 безопасно

Под **старым** дизайном резолв-но-бот-последний тред держал **счёт** положительным вечно → бесконечный цикл → поэтому `isResolved` был обязателен в review-loop.

Под **новым** дизайном сходимость **по пушу**: такой тред `review-comments` покажет один раз, юзер его скипнет (Phase 3 select/no) или ответит (reply-only) — пуша нет → цикл **корректно останавливается** (§3). `elf.24` из «критично для сходимости» превращается в «UX-полировка: не показывать резолв повторно». Значит порядок «redesign сейчас, elf.24 потом» корректен.

## §7 Scope и маршрут

- `review-loop` → `.claude/skills/` = **repo**-scope; `review-comments` → `plugins/flow/` = **flow**-scope → **отдельные коммиты** (single-package-commit).
- `review-gate.yml` + `wait_for_checks.py` (§8) — **repo**-scope, лягут в тот же коммит(ы), что и review-loop.
- Продолжаем на ветке **elf.23 / PR #100**. Старый цикл ревью на #100 ресетится — ожидаемо.

## §8 review-gate polling timeout

**Проблема.** `review-gate.yml`: `TIMEOUT=720` (12 мин). По дедлайну постит `failure`. На выходных Codex под нагрузкой отвечал ~14 мин → review-gate хлопал `failure` на 12-й минуте → `wait_for_checks` видел `review-gate` терминальным → мы завершали ожидание → ревью Codex прилетало через пару минут. Баг — преждевременный timeout-`failure`, не «pass»-ветка.

**Связка.** `wait_for_checks.py` ждёт статус `review-gate`; у него свой `WAIT_TIMEOUT=900` (15 мин). Инвариант: **`WAIT_TIMEOUT` > review-gate `TIMEOUT` + запас**, иначе локальный wait отвалится (exit 2) раньше, чем review-gate уляжется. Поэтому крутим **оба**.

**Изменения:**

| Файл | Константа | Было | Стало |
|---|---|---|---|
| `.github/workflows/review-gate.yml` | `TIMEOUT` | `720` (12 мин) | `1500` (25 мин) |
| `.claude/skills/review-loop/bin/wait_for_checks.py` | `WAIT_TIMEOUT` default | `900` (15 мин) | `1800` (30 мин) |

- Запас: 1800 − 1500 = 300s (5 мин). При норме Codex 5–8 мин и выходном пике ~14 мин — солидный резерв.
- `INTERVAL` (30s) **не трогаем** — крутим общую длительность, не частоту.
- В обоих местах добавить комментарий про инвариант связки, чтобы будущая правка одной константы не разъехалась с другой.
- Комментарий в review-gate обновить: `# ~25 min (Codex latency ~5-8 min norm; weekend spikes ~14 min)`.
- `review_gate.py` логика **не меняется** — только длительность поллинга в воркфлоу.

**Цена:** раннер поллит до 25 мин на пуш (было 12); локальный wait-ceiling 30 мин. Для этого репо приемлемо.

## §9 Тестирование

- **review-loop SKILL.md** (поведенческое) → `writing-skills` RED→GREEN + dogfood-скептик. Baseline на старом тексте, GREEN на новом. Сценарии: reply-only → ask; red-pipeline → гейт; three-way convergence; timeout-PARTIAL (сохранён); head-moved (сохранён); отсутствие GraphQL-счёта.
- **wait_for_checks.py** — меняется только дефолт `WAIT_TIMEOUT` (900→1800). Тесты переопределяют его env-переменной, поэтому существующие 12 тестов не ломаются; при желании — тривиальная проверка дефолта. Логика (wait/exit2/exit3) не трогается.
- **review-comments SKILL.md** (сентинел, поведенческое) → `writing-skills` RED→GREEN. Baseline: RC не печатает распознаваемый сигнал в no-actionable; GREEN: печатает `FLOW-REVIEW-COMMENTS: no-actionable`.
- **review-gate.yml** — CI-конфиг, юнит-тестов нет. Верификация: ревью значения + обновлённый комментарий; `review_gate.py` без изменений.

## §10 Принятые ограничения

- Сигнал review-comments — текстовый сентинел, а не структурный возврат (Skill-tool не даёт структурного возврата). Приемлемо: тот же контекст, детерминированный grep.
- review-gate 25 мин — если Codex под экстремальной нагрузкой ответит >25 мин, снова timeout-`failure`; тогда exit-2/повторный запуск. Компромисс runner-cost ↔ запас.
- Резолв-но-бот-последний тред до `elf.24` будет показан один раз за заход и скипнут юзером (не ломает сходимость — §6).
