# Review-loop redesign — Design Spec

**Дата:** 2026-07-06
**Задача:** `claude-tools-elf.23` (уточнение делверабла — скилл `review-loop` уже существует, PR #100)
**Статус:** согласован в брейншторме, готов к плану

**Ревизия 2026-07-06 (при написании плана):** сходимость упрощена до **чисто по пушу**.
Текстовый сентинел `FLOW-REVIEW-COMMENTS: no-actionable` из review-comments **исключён** —
и «нет actionable», и reply-only дают одинаковый наблюдаемый исход (**нет пуша**), а
единственное, что добавлял сентинел (авто-STOP против «спросить»), избыточно: «продолжить»
после reply-only — no-op (RC перезапустится, увидит `already_replied`, вернёт пусто, стоп).
Итог: review-comments в рамках elf.23 **не меняется**; elf.23 — целиком repo-scope.
Разделы §3/§4/§5/§6/§7/§9/§10 переписаны под это решение (исходный сентинел-вариант
сохранён в §4 как история/обоснование).

## Goal

Ужесточить разделение ответственности между `/review-loop` и `flow:review-comments`:

- **review-loop** — ждёт конец пайплайна и оркеструет цикл (запуск/остановка).
- **review-comments** — ищет и обрабатывает замечания.

Сигнал сходимости переезжает с «review-loop сам считает actionable-треды» на **«был ли новый пуш за итерацию»**. Плюс — поднять таймауты `review-gate` / `wait_for_checks`, чтобы не завершать ожидание за пару минут до медленного ревью Codex.

## Контекст (что есть сейчас)

`review-loop` (`.claude/skills/review-loop/`) каждую итерацию: ждёт пайплайн (`wait_for_checks.py`), **сам считает** actionable-треды через GraphQL `reviewThreads` (шаг 1d), и ветвит сходимость по этому счёту (шаг 1e). Это дублирует «что actionable» с `review-comments` и вынудило нас затащить в `review-loop` `isResolved`-логику (Codex round 2, коммент 3523239077). PR #100 прошёл 4 раунда ботов на текущем дизайне.

`review-comments` (`plugins/flow/skills/review-comments/`) — отдельный скилл, вызывается из `review-loop` через инструмент **Skill** (исполняется в том же контексте агента, не субагент).

## §1 Разделение ответственности

| | **review-loop** | **review-comments** |
|---|:---:|:---:|
| Ждёт конец пайплайна (`wait_for_checks.py`) | ✓ | |
| Красный пайплайн → сигнал + гейт «запускать RC?» | ✓ | |
| Запускает review-comments | ✓ | |
| Решает loop / stop (по `HEAD`-diff: был ли пуш за итерацию) | ✓ | |
| Запрашивает и обрабатывает комменты | | ✓ |
| Владеет «actionable» (already_replied, resolved) | | ✓ |

`review-loop` **больше не считает треды сам** — это целиком в `review-comments`. И **не полагается на сигнал** от review-comments: сходимость определяется наблюдаемым фактом пуша.

## §2 Итерация (control-flow)

```
a. HEAD_before = gh pr view <PR> --json headRefOid -q .headRefOid
b. PR не OPEN (merged/closed) → стоп
c. wait_for_checks.py <PR> <HEAD_before>
     exit 0  → зафиксировать список `failed` (чеки с conclusion не в {success,neutral,skipped})
     exit 1  → usage-баг вызова; чинить вызов, не трактовать как timeout
     exit 2  → timeout: plain-text prompt (НЕ AskUserQuestion):
                 1. подождать ещё   2. обработать сейчас (round = PARTIAL)   3. стоп
     exit 3  → head moved: ветка уехала во время ожидания → назад к (a)
d. ГЕЙТ красного пайплайна: `failed` не пуст → показать красные чеки, plain-text:
     1. всё равно запустить review-comments   2. стоп (чиню руками, потом перезапущу)
e. Запустить review-comments через Skill (интерактивно; может запушить новый head)
f. HEAD_after = gh pr view <PR> --json headRefOid -q .headRefOid
g. РЕШЕНИЕ о сходимости по пушу → §3
```

Ожидание пайплайна (c) остаётся **до** запуска RC, потому что CI постит ruff/ty inline-комменты; обрабатывать до окончания lint-джоба = пропустить их (early convergence). Это неизменно относительно текущего дизайна.

## §3 Решение о сходимости — чисто по пушу (заменяет старые шаги 1d/1e)

Сигнал сходимости — **был ли пуш за итерацию** (`HEAD_after` vs `HEAD_before`).
Отдельно распознавать «нет actionable» не нужно: и этот случай, и reply-only дают
одинаковый исход — **нет пуша** (см. §4).

| `HEAD_after` vs `HEAD_before` | round PARTIAL? | `failed`? | → действие |
|:---:|:---:|:---:|:---|
| изменился | — | — | **loop** → назад к (a) |
| не изменился | да (timeout+process) | — | **partial hand-off → STOP** |
| не изменился | нет | пуст | **чистая сходимость → STOP** |
| не изменился | нет | не пуст | **red-check hand-off → STOP** |

Пояснения:

- **Любой STOP без пуша — сначала проверить незапушенное.** Если review-comments применил
  фиксы, но его пуш (Phase 5.6) пропустили, коммиты лежат локально, а ответы уже заявляют
  «Fixed» — на PR фикса нет. Перед финалом сравнить локальный `git rev-parse HEAD` с
  `HEAD_after` (remote head PR-а): расходятся → предупредить «N локальных коммитов не
  запушено — ответы заявляют фиксы, которых нет на PR; запушь и перезапусти `/review-loop`».
  Это **заменяет** reply-only-«спросить»: вместо no-op-итерации — точная диагностика.
- **partial hand-off**: если раунд PARTIAL (юзер выбрал «обработать сейчас» на timeout),
  даже «нет пуша» — НЕ чистая сходимость. Репорт: «обработал что было, но пайплайн для
  `<HEAD_before>` не добежал (wait timed out) — перезапусти `/review-loop`, когда проверки
  завершатся». Сохраняется из текущего дизайна (фикс C9).
- Если STOP при непустом `failed` (путь «всё равно RC» из гейта d, либо красный чек без
  треда) → финал НЕ «чисто», а «остановился, чек `<X>` красный — чини руками». `failed`
  красит финал.
- **Сходимость ≠ mergeable.** «Боты молчат» ≠ «готово к мержу». Резолв тредов и merge
  остаются за человеком (луп reply-only; `master`-ruleset требует резолва конверсаций живым
  человеком).

**Терминаторы:** чистая сходимость (g) · partial hand-off (g) · red-check hand-off (g) · PR merged/closed (b) · юзер «стоп» на timeout-промпте (c) · юзер «стоп» на гейте красного пайплайна (d) · юзер «no» на Phase 3 внутри review-comments · юзер Esc.

## §4 Почему сходимость по пушу, а не по сигналу review-comments

Ранняя версия дизайна вводила канонический сентинел `FLOW-REVIEW-COMMENTS: no-actionable`,
который review-comments печатал бы в терминальных состояниях «нечего обрабатывать» (Edge
Cases «No Unresolved Comments» / «All Comments Already Replied» / пусто после фильтра
`already_replied`), а review-loop ловил бы через grep. **От сентинела отказались.**

Разбор: сентинел различал бы «нет actionable» и reply-only. Но оба состояния дают **один и
тот же наблюдаемый исход — отсутствие пуша** (боты создают новые треды только после пуша).
Единственное, что сентинел добавлял поверх пуш-сигнала, — авто-STOP на «нет actionable»
против «спросить стоп/продолжить» на reply-only. А «продолжить» после reply-only — **no-op**:
следующий проход review-comments увидит все треды как `already_replied`, вернёт пусто и
остановится, ничего не изменив. Значит различение не несёт пользы, но стоит кросс-скилловой
связки (правка review-comments + grep в review-loop).

Итог: review-loop решает сходимость **только по `HEAD_after` vs `HEAD_before`** (§3).
Единственный реальный пробел пуш-подхода — пропущенный пуш с локальными фиксами —
закрывается сравнением `git rev-parse HEAD` с `HEAD_after` в review-loop (§3), без правок
review-comments.

**review-comments в рамках elf.23 не меняется.** Resolved-фильтр GitHub-ветки (`isResolved`)
— по-прежнему отдельная `claude-tools-elf.24` (отложена), и теперь это **единственная**
запланированная правка review-comments для связки с review-loop.

## §5 Что удаляем / добавляем / оставляем

**Удаляем из review-loop:**
- GraphQL-счёт actionable-тредов (шаг 1d) и всё ветвление сходимости на его основе (старый 1e). Уходит ~50 строк SKILL + вся `reviewThreads`/`jq`-простыня.
- Использование `gh api graphql` и `jq`. Из `allowed-tools` убрать `Bash(jq:*)` (больше не нужен); `Bash(gh:*)` остаётся для `gh pr view` в шагах (a)/(f)/(b).

**Добавляем в review-loop:**
- Гейт красного пайплайна (шаг d): `failed` не пуст → plain-text «всё равно RC / стоп».
- Проверку незапушенного на любом STOP без пуша: `git rev-parse HEAD` vs `HEAD_after` → предупредить, если локальный head ушёл вперёд (§3, §4).

**Остаётся (хардининг 4 раундов живёт):**
- `wait_for_checks.py` целиком — включая exit 2 (timeout → PARTIAL) и exit 3 (head-moved → restart). Его `failed`-вывод кормит гейт (d) и красит финал (§3).
- Round-индикатор + `повторно`-трекинг: источник — **не** GraphQL, а собственный поитерационный вывод review-comments (его таблица Phase 2 / отчёт Phase 5.7), видимый в контексте, т.к. RC исполняется через инструмент **Skill** в том же агенте. In-session-память рефов; без персиста.
- Интерактивность вместо hard-cap; диагностика пропущенного пуша (была reply-only-caveat про skip-push).

**Переезжает, не выбрасывается:** `isResolved`-логика из счёта → в `review-comments` (elf.24).

## §6 Почему отложить elf.24 безопасно

Под **старым** дизайном резолв-но-бот-последний тред держал **счёт** положительным вечно → бесконечный цикл → поэтому `isResolved` был обязателен в review-loop.

Под **новым** дизайном сходимость **по пушу** (без какого-либо сигнала от review-comments): такой тред `review-comments` покажет один раз, юзер его скипнет (Phase 3 select/no) или ответит (reply-only) — пуша нет → цикл **корректно останавливается** (§3). `elf.24` из «критично для сходимости» превращается в «UX-полировка: не показывать резолв повторно». Значит порядок «redesign сейчас, elf.24 потом» корректен.

## §7 Scope и маршрут

- В elf.23 меняются только **repo**-scope файлы: `review-loop` → `.claude/skills/`,
  `review-gate.yml` → `.github/`, `wait_for_checks.py` → `.claude/skills/.../bin/`.
  `review-comments` (`plugins/flow/`, flow-scope) **не трогается** — вся его работа в elf.24.
  Значит single-package-commit не при делах: elf.23 целиком repo-scope.
- Разумное разбиение коммитов: (1) таймауты `review-gate.yml` + `wait_for_checks.py` (§8);
  (2) редизайн `review-loop`; плюс правка этой спеки (`docs/`, repo).
- Продолжаем на ветке **elf.23 / PR #100**. Старый цикл ревью на #100 ресетится — ожидаемо.

## §8 review-gate polling timeout

**Проблема.** `review-gate.yml`: `TIMEOUT=720` (12 мин). По дедлайну постит `failure`. На выходных Codex под нагрузкой отвечал ~14 мин → review-gate хлопал `failure` на 12-й минуте → `wait_for_checks` видел `review-gate` терминальным → мы завершали ожидание → ревью Codex прилетало через пару минут. Баг — преждевременный timeout-`failure`, не «pass»-ветка.

**Связка.** `wait_for_checks.py` ждёт статус `review-gate`; у него свой `WAIT_TIMEOUT=900` (15 мин). Инвариант: **`WAIT_TIMEOUT` > review-gate `TIMEOUT` + запас**, иначе локальный wait отвалится (exit 2) раньше, чем review-gate уляжется. Поэтому крутим **оба**.

**Изменения:**

| Файл | Константа | Было | Стало |
|---|---|---|---|
| `.github/workflows/review-gate.yml` | `TIMEOUT` | `720` (12 мин) | `1500` (25 мин) |
| `.claude/skills/review-loop/bin/wait_for_checks.py` | `WAIT_TIMEOUT` default | `900` (15 мин) | `1800` (30 мин) |

- Запас: 1800 − 1500 = 300s (5 мин). При норме Codex 5–8 мин и выходном пике ~14 мин — солидный резерв.
- `INTERVAL` (30s) **не трогаем** — крутим общую длительность, не частоту.
- В обоих местах добавить комментарий про инвариант связки, чтобы будущая правка одной константы не разъехалась с другой.
- Комментарий в review-gate обновить: `# ~25 min (Codex latency ~5-8 min norm; weekend spikes ~14 min)`.
- `review_gate.py` логика **не меняется** — только длительность поллинга в воркфлоу.

**Цена:** раннер поллит до 25 мин на пуш (было 12); локальный wait-ceiling 30 мин. Для этого репо приемлемо.

## §9 Тестирование

- **review-loop SKILL.md** (поведенческое) → `writing-skills` RED→GREEN + dogfood-скептик. Baseline на старом тексте, GREEN на новом. Сценарии: push → loop; **пропущенный пуш с локальными коммитами → предупреждение** (старый текст молча сходился по счёту); red-pipeline → гейт (d); чистая сходимость (нет пуша, `failed` пуст, не PARTIAL) → STOP; timeout-PARTIAL (сохранён); head-moved (сохранён); отсутствие GraphQL-счёта и сентинела.
- **wait_for_checks.py** — меняется только дефолт `WAIT_TIMEOUT` (900→1800, вынесен в константу `DEFAULT_WAIT_TIMEOUT`). Тесты переопределяют его env-переменной, поэтому существующие 12 тестов не ломаются; добавляется одна проверка инварианта дефолта. Логика (wait/exit2/exit3) не трогается.
- **review-comments SKILL.md** — **в elf.23 не меняется** (сентинел исключён, §4). Тестировать нечего.
- **review-gate.yml** — CI-конфиг, юнит-тестов нет. Верификация: ревью значения + обновлённый комментарий; `review_gate.py` без изменений.

## §10 Принятые ограничения

- Сходимость по пушу не различает «чистую тишину» и reply-only в тексте финального отчёта — оба это «head не изменился → STOP». Некритично: поитерационный вывод review-comments виден в контексте, а пропущенный пуш ловится сравнением `git rev-parse HEAD` с `HEAD_after` (§3, §4).
- review-gate 25 мин — если Codex под экстремальной нагрузкой ответит >25 мин, снова timeout-`failure`; тогда exit-2/повторный запуск. Компромисс runner-cost ↔ запас.
- Резолв-но-бот-последний тред до `elf.24` будет показан один раз за заход и скипнут юзером (не ломает сходимость — §6).
